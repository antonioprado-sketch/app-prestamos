2) Hallazgos del diagnóstico — por qué “no funciona” el facial

Causa #1 Secure Context

Probada: curl -k https://localhost/mediapipe/... → 200 application/wasm OK, pero si abres http://192.168.68.51 (IP sin HTTPS) el navegador bloquea getUserMedia por política. En Chrome: NotAllowedError: Only secure origins. Mensaje actual genérico no lo explica.

Causa #2 Carreras WASM

VideoIdentityPage.tsx:67-78 hace import('@mediapipe/tasks-vision') + FilesetResolver.forVisionTasks('/mediapipe/wasm'). Si el fetch del .wasm (11MB) tarda/falla, catch → "No se pudo cargar la detección" sin reintento ni pista. En 4G lento del celular puede tardar >8s y el usuario toca “Iniciar” con modelReady=false deshabilitado sin feedback.

Causa #3 Validación umbral

MIN_FACE_DETECTIONS=3:VideoIdentityPage.tsx:34 + loop requestAnimationFrame. Si la cámara arranca con poca luz, el contador queda en 0-2 y validateAndSet:187 rechaza con “No detectamos tu rostro” vaikka el video sea válido. No hay overlay guía de rostro en el preview.

Verificado ahora: WASM OK vision_wasm_internal.wasm 11.7MB sirve con Content-Type: application/wasm en nginx dev/prod (CSP worker-src 'self' blob: ok). Modelo OK 229KB. Containers: nginx Up 47m, api Up 32m. Falla es en el dispositivo, no en el build.

3) Crítica y mejora

Pedir “animación que giren el celular” suena intuitivo, pero girar el celular 90° para una INE es fricción: la mayoría sostiene el teléfono vertical. Forzar landscape rompe accesibilidad y en iOS puede reiniciar el stream. Alternativa: no exigir rotar hardware; mostrar INE horizontal dentro del preview vertical con overlay de marco apaisado + animación educativa. Teléfono vertical + INE horizontal en el marco.

4) Recomendación de Mita

No forzar landscape. Fix facial: detectar isSecureContext + banner HTTPS + retry WASM + progreso. Para INE: IneCaptureGuide.tsx 3 pasos + overlay brackets apaisado + hint “4 bordes dentro del marco” + localStorage ineGuideSeen. Solo transform/opacity 60fps.
